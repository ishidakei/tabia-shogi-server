# tabia-shogi-server

CSA プロトコルで対局する将棋サーバーです。
指定局面集を使える floodgate 互換サーバーです。[shogi-server](https://github.com/shogi-server/shogi-server) とおおむね同等で、開始局面に平手だけでなく運用者が決めた局面を使える点が異なります。指定局面として、互角局面集を設定できます。

- 実装言語: Rust
- ライセンス: GPL v3
- 状態: 開発初期

## Docker で実行する

```sh
docker build -t tabia-shogi-server .
docker run --rm -p 4081:4081 -p 8080:8080 \
  -v "$PWD/config:/etc/tabia:ro" \
  -v "$PWD/records:/var/tabia/records" \
  -v "$PWD/var:/var/tabia/db" \
  tabia-shogi-server
```

イメージが `EXPOSE` しているポートは 2 つです。4081 が CSA の待ち受け、8080 がブラウザ向けの HTTP です。どちらも設定ファイルの既定値で、`EXPOSE` はそれに合わせてあります。サーバーは HTTP でも常に待ち受けます (止める設定はありません)。ただし待ち受けの既定はループバック (`127.0.0.1`) なので、コンテナの外から見えるようにするには `[web]` に `host = "0.0.0.0"` を書きます。HTTP は平文です。TLS を張る場合はリバースプロキシで終端してください (CSA 側の `[csa.tls]` とは別の話です)。

運用に関わるものはイメージに焼き込みません。設定ファイル、局面集、TLS の証明書と鍵、棋譜の置き場所、そしてデータベースは、いずれもマウントで渡します。`config.toml` に書くパス、つまり `positions`、`records`、`database`、`[csa.tls]` は*コンテナ内の*パスなので、`/etc/tabia/positions.txt` にマウントした局面集なら、`positions` にはそのパスを書きます。棋譜のディレクトリとデータベースはサーバーが書き込む先なので `:ro` を付けず、イメージの実行ユーザー (uid 10001) が書ける権限にしておきます。上の例なら `records = "/var/tabia/records"`、`database = "/var/tabia/db/tabia.sqlite3"` です。

`auth_mode = "github"` で動かす場合は、2 つの環境変数もコンテナに渡します (下の「`[web.oauth]`」参照)。`docker run` に `-e TABIA_GITHUB_CLIENT_SECRET -e TABIA_COOKIE_KEY` を足すと、ホスト側で `export` した値が値を書かずにそのまま渡ります。

データベースはイメージに何も焼き込みません。スキーマはバイナリに埋め込んであり、起動のたびにマイグレーションを適用します。ファイル自体は運用データなので、必ずマウントしたボリュームに置いてください。コンテナのファイルシステムに置くと、コンテナを作り直した時点で対局の記録が消えます。SQLite は WAL モードで動くため、`tabia.sqlite3` と同じディレクトリに `-wal` と `-shm` の 2 ファイルができます。データベースは、この 2 ファイルも作れるディレクトリに置いてください。
イメージは非 root ユーザーで動き、設定ファイルの既定のパスは `/etc/tabia/config.toml` です。別の場所にマウントするときは、そのパスをコマンドとして渡してください。

データベースは 1 時間ごとに自動でバックアップされます。置き場所はデータベースと同じディレクトリの `.backup/` で、`tabia-<時刻>.sqlite3` の形の名前で新しい 5 世代を残します (間隔と世代数は変えられません。最初のバックアップは起動の 1 時間後です)。バックアップから戻すときは、サーバーを止めてから、`.backup/` の中の戻したい世代を `tabia.sqlite3` として差し替え、それから起動してください。サーバーが動いたまま差し替えると、戻した内容は反映されません。

止めるときは `SIGTERM` か `SIGINT` を送ります。`docker stop` が送るのは `SIGTERM`、フォアグラウンドで動かしているときの `Ctrl+C` は `SIGINT` で、どちらでも止まります。systemd の `systemctl stop` も同じです。サーバーはどちらかを受け取ると、受け取ったシグナル名をログに出し、待ち受けを閉じ、最後にデータベースを閉じて、終了コード 0 で終わります。止まったあとのディレクトリに残るのは `tabia.sqlite3` だけです。動作中に同じディレクトリにできる `-wal` と `-shm` の 2 ファイルは、止まるときに消えます。

シャットダウンの最中に届いた 2 度目のシグナルは無視します (すでに終了処理が走っているため)。進行中の対局の終了を待ちません。プロセスが終わればソケットも閉じるので、進行中だった対局の情報は失われます。終わった対局の棋譜・データベースの行はそのまま残ります。

## クイックスタート

### ビルド

```sh
cargo build --release
```

ツールチェインは `rust-toolchain.toml` で固定しています。rustup が入っていれば、バージョンを指定する必要はありません。

### 起動

```sh
target/release/tabia-shogi-server config.toml
```

引数は設定ファイルのパス 1 個だけで、既定値はありません。引数がないときも 2 個以上あるときも `usage: tabia-shogi-server <config.toml>` を表示して終了します。Docker イメージの `/etc/tabia/config.toml` はイメージがそのパスをコマンドとして渡しているだけで、サーバー自体が既定のパスを持っているわけではありません。ログは既定で info レベル、`RUST_LOG` で変更できます。

### 最小の設定ファイル

`config.toml`:

```toml
positions = "positions.txt"
records = "records"
database = "tabia.sqlite3"

[matchmaking]
idle_delay_seconds = 0
interval_seconds = 60
```

局面集は設定ファイルとは別のプレーンテキストで、`positions` が指すパスに置きます。`positions.txt`:

```text
position startpos moves 7g7f 3c3d 2g2f
position startpos moves 7g7f 3c3d 2g2f 4c4d 2f2e 2b3c 6i7h 3a2b 3i4h 5a4b
```

必ず書かなければならないのは、この 3 つのパスだけです。ほかのキーはすべて既定値を持ちます。上のファイルが既定値から変えているのは、初回の試運転向けにマッチメイキングを速めていること (下の「クライアントが送るもの」参照) だけです。CSA の待ち受けは `0.0.0.0:4081` の平文 TCP、HTTP の待ち受けは `127.0.0.1:8080`、認証は `open`、持ち時間は両者 300 秒に 1 手 10 秒加算になります。

`positions`、`records`、`database` に相対パスを書いた場合は、サーバーを起動したカレントディレクトリから解決します。`records` は終局した対局の棋譜 (CSA 形式) を 1 局 1 ファイルで書き出すディレクトリで、起動時になければ作ります。`database` は終局した対局を 1 行ずつ記録する SQLite のファイルで、こちらも起動時になければ作ります。この 2 ファイルだけで、同じホスト上の CSA クライアント 2 つで 1 局指せます。

### クライアントが送るもの

クライアントが最初に送る行は `LOGIN <name> <token>` です。`<name>` は `A-Za-z0-9_@-.` の 1〜1024 文字、`<token>` は空白を除く印字可能 ASCII (0x21〜0x7E) の 1〜64 文字で、`open` モードではこの文字種と長さに収まっていればどんなトークン文字列でも受け付けます。`LOGIN` の 2 つの引数は、CSA プロトコルの仕様でいうユーザー名とパスワードです。クライアントの設定欄が「ユーザー名 / パスワード」になっている場合は、ユーザー名にエンジン名 (`<name>`) を、パスワードにトークン (`<token>`) を書きます。エンジン名はこの文字種と長さの範囲で自由に決めた名前で、どこかに登録しておくものではありません。身元を決めるのはトークンのほうです (下の「参加者のページ」参照)。ただし、クライアントが送る行は `LOGIN` 行も含めて最初の `'` から先がコメントとして捨てられ、`tok'en` というトークンは `tok` として提示されるので、`'` だけはトークンに使えません。同じトークンで 2 つめの `LOGIN` が来ると、先のセッションが対局中でなければそれを切断して新しい側を受け付けるため、2 つのクライアントで 1 つのトークンを共有すると両方が同時に対局待ちのプールに並ぶことはありません。先のセッションが対局中の場合は逆に、新しい `LOGIN` に `LOGIN:incorrect` を返して接続を閉じ、対局中のセッションを守ります。ただし、対局中のまま 1 日を超えて何も送ってこないセッションは別で、同じトークンの新しい `LOGIN` が来るとそちらを受け付け、古いセッションを切断します。クライアントごとに別の文字列を使ってください。受理されると `LOGIN:<name> OK` が返り、そのセッションは対局待ちのプールに入ります。誰と誰を組み合わせるかを決めるのはマッチメイキングのラウンドです。次のラウンドは前のラウンドの `interval_seconds` (既定 1800 秒) 後に走りますが、サーバー上の対局が 0 になったときは、その `idle_delay_seconds` (既定 60 秒) 後まで前倒しされます (そちらが早い場合)。起動直後の最初のラウンドも起動から `idle_delay_seconds` 後です。上の設定ファイルは初回の試運転向けに、`[matchmaking]` の `interval_seconds` を 60 秒、`idle_delay_seconds` を 0 秒にしてあります。組み合わせが決まると両者に `Game_Summary` が届くので、それぞれ `AGREE` を返せば対局が始まります。

## ブラウザで対局を見る

サーバーは HTTP でも常に待ち受けます。アドレスを変えるのが `[web]` の `host` と `port` で、既定は `127.0.0.1:8080` です。アカウントの要らないページが 5 つあります。`GET /` が対局一覧で、対局中のものを先に、終局したものを新しい順に並べます。どちらの行も開始時刻 (UTC) がその対局のページへのリンクです。`GET /games/<Game_ID>` が対局のページで、対局中なら盤面・手数・最終手・両者の残り時間を、終局済みなら対局者名・開始と終局の時刻・結果・終局理由・手数と、棋譜へのリンクを表示します。`GET /games/<Game_ID>/record` が棋譜そのもので、`text/plain; charset=utf-8` として、終局時にディスクへ書いた `.csa` をそのまま返します。`.csa` は CSA 標準棋譜形式の棋譜で、対局者名・持ち時間の条件・開始局面 (セットアップ手順込み)・指し手と 1 手ごとの消費時間・終局と結果が入っています。

対局中のページは自動更新しません。

一覧は終局した対局を新しい順に 100 局まで表示し、それより古いものは末尾の「これより前の対局」リンク (`?before=<終局時刻>`) からたどります。JavaScript は使っていません。

## 参加者のページ

`GET /participants` が参加者の一覧です。参加者はエンジンごとに数えます。エンジンを見分けるのはログインに使ったトークンで、トークンが異なれば別のエンジンとして扱い、同じトークンで別のエンジン名を名乗った対局は 1 つのエンジンとしてまとめます。以降この文書では、対局しレーティングが付く側をエンジンと呼び、トークンという語は発行・失効・`LOGIN` に書く資格情報そのものを指すときにだけ使います。名前はそのエンジンが最後に対局したときに名乗ったエンジン名です。ここに並ぶのはこのサーバーで 1 局でも終局したエンジンだけで、トークンを発行しただけで対局していないものは出ません。

一覧の各行は `GET /participants/<参加者 ID>` へのリンクです。参加者のページはその参加者の対局を新しい順に 100 局まで並べ、1 行ごとに対局のページと棋譜へのリンクを出します。それより古いものは対局一覧と同じ「これより前の対局」リンクからたどります。つまり、参加者一覧 → 参加者のページ → 棋譜まで、リンクだけで行き止まりなくたどれます。

`<参加者 ID>` は、ログイン時に提示されたトークンの SHA-256 を 16 進で書いたものです。`games` テーブルに記録しているのと同じ値で、トークンそのものではありません。ここからトークンを復元することはできず、サーバーもトークンを保存していません。

`github` モードでは、そのエンジンの持ち主の GitHub の情報も出しますが、出るのはその持ち主が GitHub のアカウントを公開すると選んだ場合だけです。公開は 3 項目まとめてなので、出るときはユーザー ID・アカウント名・アバター画像の URL の 3 つとも出て、公開していなければ (初期状態) GitHub の欄そのものが出ません。`open` モードにはアカウントがないので、GitHub の欄は常に出ません。

レーティングは下の「レーティング」の節の条件を満たしたエンジンにだけ付きます。満たしていない参加者のページには「未算定」と出ます。

## レーティング

`GET /ratings` が通算の表、`GET /ratings/recent` が直近 2 週間の表です。どちらも同じ算定を、読む対局の範囲だけ変えて行ったものです。定期的に (既定では 15 分ごとに) 作り直していて、対局が終わった時点では何も動かず、次の作り直しで表に反映されます。運用側の操作は要りません。

更新の時刻は UTC の 0 時から間隔ごとに区切ったところに揃えます。既定の 900 秒なら毎時 :00、:15、:30、:45 です。サーバーをいつ起動しても更新の時刻は同じで、表の「最終算定」に出る時刻もきりのよい値になります。起動直後の 1 回だけはこの区切りを待たず、その場で 1 回作ります。

算定の方法は floodgate と同じです。

- 全履歴からの一括の最尤推定です。1 局ごとにレーティングを足し引きする処理はサーバーのどこにもありません。
- 古い対局ほど軽く数えます。半減期は 60 日、最初の 7 日は減衰なし、2 年より古い対局は読みません。
- 引き分けは両者に 0.5 勝 0.5 敗として数えます。
- 表に載るのは、重み付けの成績で 1 勝以上・1 敗以上・15 局以上を満たしたエンジンだけです。この判定は繰り返し行います。条件を満たさないエンジンを外すとその対局も消えるので、いったん満たしていたエンジンが満たさなくなることがあり、外す作業は変化がなくなるまで続きます。
- 切断で終わった対局は、両者が実際に指した手数が 30 手以下なら、レーティングの算定に入れません。31 手以上なら、記録どおりの勝敗として数えます。ここで数えるのは指した手数だけで、開始局面に進めるためにサーバーが送った手順は含みません。

最尤推定が決めるのはエンジン同士の差だけで、レートの絶対的な数値は決まりません。数値は、運用者が与える基準 (一部のエンジンへの指定レート、または指定レートが無いときに表の平均をそろえる値) から決まります。floodgate の数値とは合いません。

- 運用者は、任意のエンジンに指定レートを与えられます。指定レートはレートの絶対的な数値を決めるための基準値であって、そのエンジンのレートの表示値を固定するものではありません。指定レートを与えられたエンジンも、そのエンジンのレートとして表示されるのは、算定した値です。指定レートが算定に入ることもありません。
- 指定レートをどこに書くかは、エンジンの種類で分かれます。プリセットエンジンには設定ファイルで与えます (`[matchmaking].preset_engine_tokens` の `rating`。変更には再起動が要ります)。それ以外のエンジンには、運用者がブラウザの管理ページで与えます (下の「指定レートの管理ページ」参照)。こちらはデータベースに入り、変更は次回のレーティングの更新から効きます。再起動は要りません。
- 指定レートを持ち、上の条件を満たしたエンジンが 1 つ以上いる場合、そのエンジンと対戦関係でつながっているエンジンだけが表に載ります。平行移動はこのつながり (グループ) ごとに行い、移動幅は、そのグループ自身が持つ指定レート持ちエンジンの (指定レート − 算定値) の平均です。グループはそれぞれ、自分のグループの指定レートが定める尺度に載ります。
- 条件を満たした指定レート持ちが 1 つもいない場合は、対戦相手の種類がもっとも多いエンジンと、対戦関係でそこにつながっているエンジンを載せ、その平均が `fallback_baseline` (既定 3500) になるようそろえます。
- 通算の表と直近 2 週間の表は、この判断をそれぞれの対局範囲で別々に行います。レートの絶対的な数値も、載るエンジンも、2 つの表で違うことがあります。

表の各行は参加者のページへのリンクです。プリセットエンジンもほかの参加者と同じように並びます。

## トークンのページ

サインインしたアカウント向けのページが 3 つあります。`GET /tokens` がトークンの一覧で、1 本ごとに最後にログインしたエンジン名、レーティング、発行時刻、有効か失効かを出します。`POST /tokens/issue` が発行で、トークンの値を表示するのはこのときの 1 回だけです。サーバーはハッシュしか保存しないので、後から見る手段はありません。`POST /tokens/revoke` が失効で、失効させたトークンは次のログインから通らなくなります。再起動は要りません。

上限に達している場合、発行のページはどちらの上限に当たったのかと、それに対して何ができるのかを出します。失効させればアクティブの枠は空き、発行累計の枠は空きません (`[accounts]`)。

`[web].administrators` に書いたアカウントには、この 2 つの上限をどちらも適用しません (下の「`[accounts]`」参照)。そのアカウントの一覧のページは、本数の横に上限の数を出さず、上限が適用されない旨を出します。発行のフォームも常に出ます。

そのアカウントがレーティングの付いたエンジンを 1 つ以上持っている場合にかぎり、発行のときに仮のレーティングを付けられます。上限はそのアカウントのレーティングの付いたエンジンのうち最も高い値で、それを超える値を書くと、トークンは発行されず、上限の値を示したページが出ます。1 つも付いていないアカウントにはこの欄そのものが出ません。

仮のレーティングを読むのはマッチメイキングだけです。まだレーティングの付いていないエンジンについて、組み合わせを決めるときの見積もり (`[matchmaking].unrated_estimate`、既定 3000) の代わりに使います。そのエンジンにレーティングが付いているあいだは、算定した値のほうを使います。対局が途絶えて、レーティングの条件 (下の「レーティング」参照) を満たさなくなったあとは、また仮のレーティングを読みます。仮のレーティングは算定にも、レーティングの表にも入りません。

この 3 つはサインインしたセッションからしか開けません。サインインしていなければ 401 を返し、そのページから `GET /sign-in` へのリンクを出します。

## アカウントのページ

`GET /account` は、サインインしているアカウントのページです。サーバーが GitHub から取得して保存するのは、ユーザー ID・アカウント名・アバター画像の URL の 3 つだけです。メールアドレスやリポジトリの情報は取得しません。ページはこの 3 つと、これらをほかの人に見せるかどうかの設定を出します。

公開範囲の設定は 1 つで、3 項目まとめて公開するかしないかを決めます。初期状態では公開しません。ページのボタンが `POST /account/visibility` で、押すと公開と非公開が入れ替わります。切り替えた結果は次の表示からそのまま反映されます。運用側の操作も再起動も要りません。

ほかの人が見るページに出るのは、公開にした場合の 3 項目です。公開していなければ、ほかの人が見るページのどこにも出ません。自分の参加者ページは、サインインしていれば公開していなくても 3 つとも見えます。設定はほかの人に対するもので、持ち主自身の見え方は変えないからです。

この 2 つもトークンのページと同じサインインの境界の内側にあるので、サインインしていなければ 401 を返します。アカウントのページの末尾にはサインアウトのボタン (`POST /sign-out`) があります。

## 指定レートの管理ページ

レーティング表のレートの絶対的な数値は、運用者が与える指定レートが決めます (上の「レーティング」参照)。プリセットエンジン以外のエンジンへの指定レートは、このページで設定します。設定ファイルには書きません。

`GET /admin/ratings` がそのページです。表が 2 つあります。1 つ目はいま設定している指定レートの一覧、2 つ目は指定レートを与えられるエンジン — このサーバーで対局を終えたエンジンのうち、プリセットエンジンでなく、まだ指定レートを持たないもの — の一覧です。どちらの表も 1 行ごとに指定レートの入力欄と保存のボタンを持ち、押すと `POST /admin/ratings/designate` になります。1 つ目の表で入力欄を空にして保存すると、その指定レートを削除します。指定レートを与えられるのは対局を終えたエンジンだけで、1 局も終えていないエンジンには設定できません。

ここでの変更は次回のレーティングの更新から効きます。設定した値はデータベースに入り、レーティングを作り直すたびに読み直すので、再起動は要りません。対局中の対局にも影響しません。

プリセットエンジンはここでは設定できません。プリセットエンジンの指定レートは、そのエンジンを登録している設定ファイルの項目 (`[matchmaking].preset_engine_tokens` の `rating`) が決めます。変更には再起動が要ります。

このページを使えるのは `[web].administrators` に書いたアカウントでサインインしている場合だけです。それ以外のアカウントでサインインしている場合は 404 を返し、どのページからもこのページへのリンクは出しません。サインインしていない場合は、ほかのサインインが要るページと同じ 401 です。`auth_mode = "open"` のインスタンスにはこの 2 つの経路がそもそもありません (404 です)。

## GitHub でサインインする

`auth_mode = "github"` の場合にかぎり、サインインの経路が 3 つ増えます。`GET /sign-in` が入口で、github.com の認可ページに転送します。`GET /sign-in/callback` が戻り先で、ここでセッションを作ってアカウントのページへ送ります。`POST /sign-out` がサインアウトで、サーバー側のセッションを消してクッキーも消します。`auth_mode = "open"` のインスタンスにはこの 3 つがそもそもありません (404 です)。

要求する OAuth スコープはありません。GitHub の既定の許可で得られるのは公開プロフィールで、サーバーが保存するユーザー ID・アカウント名・アバター画像の URL の 3 つはちょうどその範囲です。メールアドレスもリポジトリの情報も要求しませんし、保存する場所もありません。初回のサインインでアカウントを作り、2 回目以降は同じアカウントに入ります。公開範囲の設定はサインインし直しても変わりません。

セッションはサーバー側に持ち、ブラウザには署名したランダムな ID をクッキー (`tabia_session`) で渡します。属性は `HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/` です。有効期間は 12 時間で、サーバーを再起動すると全員サインアウトされます。セッションはメモリにしか置いていないためで、もう一度サインインすればすぐ戻ります。署名が合わないクッキーはエラーではなく、サインインしていない状態として扱います。

### 運用側の準備

1. GitHub で OAuth App を 1 つ作ります。Authorization callback URL には、そのインスタンスの `https://<ホスト名>/sign-in/callback` を登録してください。この URL は設定ファイルには書きません (GitHub 側の登録をそのまま使います)。
2. 発行された Client ID を設定ファイルの `[web.oauth]` に書きます。
3. Client secret と、クッキーの署名鍵を環境変数で渡します。

```sh
export TABIA_GITHUB_CLIENT_SECRET='...'          # OAuth App の client secret
export TABIA_COOKIE_KEY="$(openssl rand -hex 32)" # 小文字 16 進 64 文字
```

この 2 つは設定ファイルに書けません (`[web.oauth]` に `client_secret` と書くと、そのキー名を表示して起動を中止します)。設定ファイルは局面集を足したり上限を変えたりするために日常的に開くファイルで、そこに秘密を置かないための切り分けです。

`auth_mode = "github"` でこの 3 つのうちどれかが欠けている場合は、欠けているものを全部並べて起動を中止します。

準備はインスタンスごとにこの 1 回だけです。ユーザーごとの操作はありません。

## 設定リファレンス

設定ファイルは TOML です。どの階層でも、知らないキーが 1 つあれば起動時エラーになり、そのキー名が表示されます。設定を無視して起動することはありません。`auth_mode`、`time_unit`、`side` に知らない値を書いた場合も同様で、受け付ける綴りを並べて起動時エラーになります。

### トップレベル

| キー | 型 / 値 | 必須・既定 | 意味 |
| --- | --- | --- | --- |
| `auth_mode` | `"github"` または `"open"` | 既定 `"open"` | ログインの認証方法。`open` はどんなトークン文字列も受け付ける |
| `positions` | 文字列 (パス) | 必須 | 局面集ファイルのパス |
| `records` | 文字列 (パス) | 必須 | 終局した対局の棋譜を書き出すディレクトリ |
| `database` | 文字列 (パス) | 必須 | 終局した対局を記録する SQLite ファイル |

必須なのはこの 3 つのパスだけです。ほかのキーもテーブルもすべて既定値を持つので、設定ファイルはこの 3 行だけでも起動します。パスに既定値を置かないのは、書いた覚えのない場所にサーバーが棋譜やデータベースを作るのを避けるためです。

`records` は起動時になければ作ります (`mkdir -p` と同じ)。作れない場合、あるいは作れても書き込めない場合は、キー名とパスを表示して起動を中止します。対局が終わってから書けないと分かるのでは遅いためで、確かめ方は実際に書いてみる方法です。棋譜は 1 局 1 ファイル、名前は `<Game_ID>.csa` で、ファイルを書き終えて `fsync` してから終局の 3 行をクライアントに送ります。

棋譜と同じディレクトリに、同じ名前で拡張子だけが違う `<Game_ID>.meta` も書き出します。同じ対局の記録を復元用に控えたファイルです。棋譜と同じく `fsync` してから終局の 3 行を送ります。こちらはサーバー内部用で、web からは取得できません。対局の識別情報 (ログイン時に提示されたトークンの SHA-256、トークンそのものではありません)、開始局面と持ち時間の区分、結果を持っていて、`games` の行を作り直すのに必要なものはこのファイルだけで揃います。棋譜は公開する成果物なのでトークンに関わるものを書けず、対局者名からトークンは引けないため、この 2 ファイルに分けています。バックアップやコピーのときは、棋譜と `.meta` を必ず一緒に扱ってください。

`database` も起動時になければ作ります。開けない場合、あるいはマイグレーションに失敗した場合は、キー名とパスを表示して起動を中止します。行は終局の 3 行を送った*あと*に書きます。ここで書けなくてもその対局には影響せず、次回の起動時に `.meta` を読んで行のない対局を復旧します (`reconciled N games` と表示します)。読めない `.meta` はパスを表示して読み飛ばすだけで、消しません。

`github` を指定すると、`LOGIN` のトークンは発行済みのトークンとして照合します。提示された文字列の SHA-256 を `tokens` テーブルから引き、見つからないもの・失効させたものは同じく `LOGIN:incorrect` です。ログインが通ると、そのトークンの表示名をこのときの `<エンジン名>` で上書きします。`open` はどんなトークン文字列も受け付け、`tokens` テーブルを一切読みません。サインインの経路もありません。

トークンの発行はブラウザからのサインイン (GitHub SSO) でしか行えないので、`github` を指定した場合は OAuth App の設定が必須です。`[web.oauth]` の `client_id` と、2 つの環境変数 `TABIA_GITHUB_CLIENT_SECRET`、`TABIA_COOKIE_KEY` を揃えてください (上の「運用側の準備」参照)。どれかが欠けていれば、欠けているものを全部並べて起動を中止します。

### `[limit]` (テーブルごと省略可)

省略すると総手数は無制限で、余白の規則も働きません。書く場合は 2 キーとも必須で、片方だけでは起動しません。

| キー | 型 / 値 | 必須・既定 | 意味 |
| --- | --- | --- | --- |
| `max_moves` | 整数 (0〜4294967295) | テーブルを書くなら必須 | `Max_Moves`。開始局面の手順も含めた総手数の上限 |
| `min_playable_plies` | 整数 (0〜4294967295) | テーブルを書くなら必須 | 局面集の各エントリで、`max_moves` から手順の手数を引いた残り (実際に指せる手数) がこの値以上でなければならない (下の「局面集」参照) |

型の範囲以外に上限・下限の検査はありません。

### `[accounts]` (テーブルごと省略可)

1 つのアカウントが持てるトークンの本数の上限です。キーがすべて既定値を持つので、テーブルごと省略できます。

| キー | 型 / 値 | 必須・既定 | 意味 |
| --- | --- | --- | --- |
| `active_token_cap` | 整数 1 以上 | 既定 3 | 同時に有効にしておけるトークンの本数。0 は起動時エラーになる |
| `lifetime_token_cap` | 整数 1 以上 | 既定 16 | これまでに発行したトークンの本数の上限。失効させたものも数に入る。0 は起動時エラーになる |

2 つは数えているものが違います。`active_token_cap` は失効させていない行を数えるので、1 本失効させると枠が 1 つ空きます。`lifetime_token_cap` は発行した行をすべて数えるので、失効させても枠は空きません。前者は 1 つのアカウントが同時に動かすエンジンの数を、後者は身元の作り直しの回数を抑えるためのもので、この非対称がねらいです。

上限を確かめるのは発行のときだけです。上限を下げて、それを超えているアカウントがあっても、既存のトークンはそのままログインでき、ページもそのまま出ます。できなくなるのは新しい発行だけです。上げる場合はそのまま枠が増えます。どちらも設定ファイルの編集と再起動だけです。

`[web].administrators` に書いたアカウント (下の「`[web]`」参照) には、この 2 つをどちらも適用しません。

適用するかどうかは発行のたびに設定ファイルから読みます。アカウントに印を付けるわけではないので、`administrators` から外せば次の発行から 2 つの上限がまた効き、それまでに発行したトークンはそのまま残ってログインできます。上限を下げたときと同じで、できなくなるのは新しい発行だけです。

`active_token_cap` が `lifetime_token_cap` より大きい設定も起動しますが、発行は必ず先に `lifetime_token_cap` に当たるため `active_token_cap` は効きません。警告をログに出します。

### `[ratings]` (テーブルごと省略可)

レーティング表を作り直す間隔と、指定レートを持つエンジンがいないときに表の平均をそろえる値です。キーがすべて既定値を持つので、テーブルごと省略できます。

| キー | 型 / 値 | 必須・既定 | 意味 |
| --- | --- | --- | --- |
| `update_interval_seconds` | 整数 1 以上、86400 の約数 | 既定 900 | 2 つのレーティング表を作り直す間隔 (秒)。0 と、86400 を割り切れない値は起動時エラーになる |
| `fallback_baseline` | 整数 | 既定 3500 | 条件を満たした指定レート持ちが 1 つもいないときに、表に載るグループの平均をそろえる値 |

86400 (1 日の秒数) の約数だけを受け付けるのは、更新を UTC の 0 時から間隔ごとに区切った時刻に揃えているからです。900 なら毎時 :00、:15、:30、:45 で、これは起動した時刻によらず同じです。割り切れない値だとこの区切りが日をまたぐたびにずれるので、キー名と 86400 を表示して起動を中止します。

プリセットエンジン以外のエンジンへの指定レートは、ここには書きません。ブラウザの管理ページで設定してデータベースに入ります (上の「指定レートの管理ページ」参照)。プリセットエンジンへの指定レートは、`[matchmaking].preset_engine_tokens` の各要素の `rating` です (下の「プリセットエンジン」参照)。管理ページで設定した参加者があとからプリセットエンジンになった場合は、設定ファイル側の値を使います。

レーティングの算定そのもののパラメータ — 60 日の半減期、最初の 7 日は減衰なし、2 年より古い対局は読まない、1 勝 1 敗 15 局の下限、切断局を数えない 30 手のしきい値 — は floodgate と同じ値で、設定ではなく定数です。

なお、起動直後の 1 回目はこの間隔を待ちません。

### `[csa]` (テーブルごと省略可)

CSA の待ち受けの設定です。キーがすべて既定値を持つので、テーブルごと省略できます。テーブル名がプロセス全体ではなく CSA を指しているのは、同じプロセスが HTTP も待ち受けるからです (`[web]`)。

| キー | 型 / 値 | 必須・既定 | 意味 |
| --- | --- | --- | --- |
| `host` | 文字列 | 既定 `"0.0.0.0"` | 待ち受けるインターフェース |
| `port` | 整数 0〜65535 | 既定 4081 | 待ち受けるポート。4081 は floodgate と同じ番号。0 は空きポートを自動で選ぶ |
| `max_malformed_lines` | 整数 1 以上 | 既定 8 | 不正な行が何行でその接続を切るか。0 は起動時エラーになる |
| `agreement_timeout_seconds` | 整数 (0 以上) | 既定 120 | 提示した組み合わせが両者の `AGREE` を待つ秒数 |

IPv6 のアドレスは角かっこなしで書きます (`host = "::1"`)。角かっこはサーバーが付けます。

このアドレスに束縛できない場合は、アドレスを表示して起動を中止します。

`max_malformed_lines` と `agreement_timeout_seconds` は対局の時間ではなく運用の設定なので、`time_unit` は適用されません。秒であることはキー名が示しています。

### `[csa.tls]` (テーブルごと省略可)

テーブルがなければ待ち受けは平文の TCP、書けば TLS です。証明書だけ、鍵だけは起動しません。

| キー | 型 / 値 | 必須・既定 | 意味 |
| --- | --- | --- | --- |
| `cert` | 文字列 (パス) | テーブルを書くなら必須 | PEM の証明書チェーン。リーフが先頭 |
| `key` | 文字列 (パス) | テーブルを書くなら必須 | そのリーフに対応する PEM 秘密鍵 |

ファイルが実在するか、鍵と証明書が対になっているかは、待ち受けを組み立てる時点で確かめます。

### `[web]` (テーブルごと省略可)

サーバーは HTTP でも常に待ち受けます。CSA の待ち受けと同じプロセス、同じランタイムです。HTTP を止める設定はありません。このテーブルが決めるのはどのアドレスで待ち受けるかと、誰を運用者とするかで、キーはすべて既定値を持つのでテーブルごと省略できます。省略は「既定のアドレス (`127.0.0.1:8080`) で待ち受ける」という意味で、中身が空の `[web]` と同じです。

| キー | 型 / 値 | 必須・既定 | 意味 |
| --- | --- | --- | --- |
| `host` | 文字列 | 既定 `"127.0.0.1"` | 待ち受けるインターフェース |
| `port` | 整数 0〜65535 | 既定 8080 | 待ち受けるポート。0 は空きポートを自動で選ぶ |
| `administrators` | 整数の配列 | 既定 `[]` | このサーバーの運用者とする GitHub アカウントのユーザー ID |

`host` の既定が `[csa]` と違ってループバックなのは、こちらが平文の HTTP だからです。ネットワークに出すのは運用者が決めることなので、`host = "0.0.0.0"` は書かないかぎり有効になりません。

このアドレスに束縛できない場合は、アドレスを表示して起動を中止します。平文の HTTP のみで、`[csa.tls]` に相当するキーはありません。TLS はリバースプロキシで終端してください。

`administrators` に書いたアカウントでサインインすると、指定レートの管理ページが使えます (上の「指定レートの管理ページ」参照)。それ以外のアカウントには、このページへのリンクも出ませんし、アクセスもできません。

もう 1 つ、`administrators` に書いたアカウントには `[accounts]` のトークンの本数の上限を適用しません (上の「`[accounts]`」参照)。このほかに管理者のアカウントとふつうのアカウントの違いはありません。

書くのはアカウント名ではなくユーザー ID (整数) です。`https://api.github.com/users/<アカウント名>` の `id` がその値です。ID を使うのは、これがサインインしたセッションがそのまま持っている値であることと、GitHub がユーザー ID を再利用しないことによります。アカウント名は改名でき、空いた名前は別の人が取得できるので、名前で書くと設定ファイルを 1 行も変えないまま管理権限が別人に移りうるからです。

`auth_mode = "open"` のインスタンスにはアカウントがないので、ここに書いても誰もそのアカウントでサインインできません。この場合は効果がない旨を警告して起動します。管理ページの経路もそもそも作りません。

### `[web.oauth]` (テーブルごと省略可)

GitHub でのサインインに使う OAuth App です。`auth_mode = "github"` の場合は必須で、欠けていれば起動を中止します。`auth_mode = "open"` に書いた場合は、どこからも読まない旨を警告して起動します。

| キー | 型 / 値 | 必須・既定 | 意味 |
| --- | --- | --- | --- |
| `client_id` | 文字列 | テーブルを書くなら必須 | OAuth App の Client ID。公開値で、認可 URL にそのまま載る |

このテーブルに書けるのはこのキーだけです。client secret とクッキーの署名鍵は環境変数 `TABIA_GITHUB_CLIENT_SECRET` と `TABIA_COOKIE_KEY` で渡します。戻り先の URL も、github.com の API のアドレスも、キーにはしていません。戻り先は GitHub 側の登録をそのまま使います。

### `[time]` (テーブルごと省略可)

数値はすべて `time_unit` の個数で、書いた数値がそのまま `Game_Summary` の `Time` ブロックに載ります。単位の掛け算はサーバーの内部だけの話で、通信文と設定ファイルの数値は一致します。キーがすべて既定値を持つので、テーブルごと省略できます。既定値は floodgate がいま使っている持ち時間です。

| キー | 型 / 値 | 必須・既定 | 意味 |
| --- | --- | --- | --- |
| `time_unit` | `"1sec"`、`"1min"`、`"1msec"` | 既定 `"1sec"` | 以下の数値の単位。`Time_Unit` としてそのまま送る |
| `total` | 整数 (0〜4294967295) | 既定 300 | `Total_Time`。持ち時間 |
| `byoyomi` | 整数 (0〜4294967295) | 省略可 (省略は秒読みなし) | `Byoyomi` |
| `increment` | 整数 (0〜4294967295) | 既定 10 | `Increment`。手番が始まる前に加算する。加算なしにするには `0` と書く |
| `least_time_per_move` | 整数 (0〜4294967295) | 既定 0 | `Least_Time_Per_Move`。1 手で必ず消費する下限 |
| `roundup` | 真偽値 | 既定 `false` | `Time_Roundup`。単位未満の消費を切り上げるか切り捨てるか |

既定値が効くのは書かなかったキーだけです。単位も既定値のひとつなので、`time_unit = "1min"` だけを書いたテーブルは 300 分に 1 手 10 分加算になります。数値は書いた単位の個数だという規則が、既定値にもそのまま当てはまるためです。

`increment` だけは既定が「値」なので、加算なしにしたい場合は `increment = 0` と明示します。0 は加算しないという意味で、`Increment:0` として通信文と棋譜に載ります。`byoyomi` の既定は「なし」のままです。

### `[time.reduction]` (テーブルごと省略可)

テーブルがなければ両者同じ持ち時間です。書けば片方の持ち時間だけを減らせます。

| キー | 型 / 値 | 必須・既定 | 意味 |
| --- | --- | --- | --- |
| `side` | `"black"` または `"white"` | テーブルを書くなら必須 | 持ち時間を減らす側 |
| `amount` | 整数 (0〜4294967295) | テーブルを書くなら必須 | 減らす量。`time_unit` の個数 |

減らした分は `Time` ブロックには出ません。開始局面の手順の T 値に載せて送るので、載せる先のない組み合わせは起動時エラーになります (次の項)。

### `[matchmaking]` (テーブルごと省略可)

キーがすべて既定値を持つので、テーブルごと省略できます。

| キー | 型 / 値 | 必須・既定 | 意味 |
| --- | --- | --- | --- |
| `idle_delay_seconds` | 整数 (0 以上) | 既定 60 | 起動直後、およびサーバー上の対局が 0 になった直後から次のラウンドまでの秒数。0 も設定として有効 |
| `interval_seconds` | 整数 1 以上 | 既定 1800 | ラウンドとラウンドの間隔の上限 (対局が 0 になると前倒しされる。上の「クライアントが送るもの」)。0 は起動時エラーになる |
| `first_round_at` | RFC 3339 の文字列、または `""` | 既定 なし | 起動後の最初のラウンドの時刻。未設定、空文字列、過去の時刻のいずれでも「起動時刻 + `idle_delay_seconds`」になる |
| `unrated_estimate` | 整数 | 既定 3000 | まだレーティングの付いていないエンジンを、組み合わせを決めるときに何点として扱うか |
| `preset_engine_tokens` | テーブルの配列 | 既定 `[]` | プリセットエンジンの一覧。1 要素が 1 エンジンで、`token` (必須)、`protocol` (省略可、既定 `"csa"`)、`rating` (省略可、指定レート) を持つ。`protocol = "usi"` の要素はさらに `command` と `lifecycle` を持つ |

`unrated_estimate` を読むのは組み合わせの計算だけです。直前の対局の相手にレーティングが付いていればそちらから見積もるほうが優先で、仮のレーティング (上の「トークンのページ」参照) があればそれが優先です。この値は算定にもレーティングの表にも入らず、この値で見積もられたエンジンはほかのどの規則から見てもレーティングなしのエンジンのままです。1 局も指していないプリセットエンジンをどれだけの強さとみなすかにも、同じ値を使います。

`interval_seconds` が `idle_delay_seconds` より小さい設定は起動しますが、対局が終わってからのラウンドは常に間隔のほうが先に来るため、警告をログに出します。

#### プリセットエンジン

プリセットエンジンは、運用者があらかじめ用意しておく、強さの決まった対戦相手です。動かし方は 2 通りあり、`protocol` で決まります。

- `protocol = "csa"` (既定): CSA プロトコルを話すエンジンを、運用者が自分で動かします。置き場所はどこでもよく (同じホストでも別のホストでも)、ふつうのクライアントとして CSA の待ち受けにログインします。サーバーはこのエンジンを起動も停止も再起動もしません。サーバーがするのはトークンの照合だけです。それ以外は他のプリセットとまったく同じで、指定レートも同じように効き、対局もふつうの対局です。
- `protocol = "usi"`: USI を話すだけのエンジンを、サーバーが起動します。エンジンとのやりとりは標準入出力の USI で、CSA の側はサーバーが引き受け、ループバック接続でこのサーバー自身の待ち受けにこの要素の `token` でログインします。したがってこのエンジンの対局もふつうの対局です。ログイン、組み合わせ、レーティング、棋譜、ページのどこにも特別扱いはありません。運用者が USI と CSA を変換する仕組みを用意する必要はありません。

`preset_engine_tokens` の各要素が 1 エンジンで、次のキーを持ちます。`protocol` に応じて、使わないキーは書くと起動時エラーになります (書いても効かないキーを黙って無視しないため)。

| キー | 型 / 値 | `protocol = "csa"` | `protocol = "usi"` | 意味 |
| --- | --- | --- | --- | --- |
| `token` | 文字列 | 必須 | 必須 | このエンジンが `LOGIN` で提示するトークン。提示された文字列とバイト単位で比較する |
| `protocol` | `"csa"` / `"usi"` | 省略可 (既定 `"csa"`) | — | このエンジンが話すプロトコル |
| `rating` | 整数 | 省略可 | 省略可 | このプリセットへの指定レート。レートの絶対的な数値を決めるための基準値で、上の「レーティング」を参照 |
| `command` | 文字列の配列 | 書けない | 必須 | エンジンを起動するコマンド。先頭がプログラム、残りが引数 |
| `lifecycle` | `"resident"` / `"on-demand"` | 書けない | 必須 | プロセスをいつ動かすか (下記) |
| `usi_options` | テーブル | 書けない | 省略可 | エンジンに設定する USI オプション。`usi` と `isready` の間に 1 行 1 つの `setoption` として送る |
| `name` | 文字列 | 書けない | 省略可 | `LOGIN` で名乗る名前。省略するとエンジン自身の `id name` を使う |

`token` に書く文字列をどう用意するかは、`auth_mode` (上の「トップレベル」参照) で分かれます。

- `auth_mode = "open"`: `LOGIN` はどんなトークン文字列も受け付けるので、運用者が文字列を自分で決めます。決めた文字列をこの `token` に書き、同じ文字列をそのエンジンのクライアントにも渡します。制約は下に挙げるもの (空でない、空白を除く印字可能 ASCII、64 文字以内、`'` を含まない) だけです。
- `auth_mode = "github"`: `LOGIN` は発行済みのトークンしか受け付けないので、運用者がサインインし、トークンのページ (上の「トークンのページ」参照) でトークンを 1 本発行します。そのとき 1 回だけ表示される値をこの `token` に書き、同じ値をそのエンジンのクライアントにも渡します。発行したアカウントが `[web].administrators` に入っていれば、`active_token_cap` と `lifetime_token_cap` はどちらも適用されません (上の「`[accounts]`」参照)。入っていなければ、このトークンもほかのトークンと同じように 2 つの上限に数えます。

```
[matchmaking]
preset_engine_tokens = [
  { token = "first-engine-token", protocol = "usi", lifecycle = "on-demand",
    command = ["/opt/tabia/engine-a", "--quiet"],
    usi_options = { USI_Hash = 256, BookFile = "/opt/tabia/book.bin" } },
  { token = "reference-engine-token", protocol = "usi", lifecycle = "resident",
    command = ["/opt/tabia/engine-b"], name = "reference-engine", rating = 1800 },
  { token = "outside-engine-token", rating = 2200 },
]
```

3 つめの要素には `protocol` がありません。既定の `"csa"` なので、このエンジンは運用者が自分で動かし、`outside-engine-token` でログインしてきたところをサーバーがこのプリセットとして認識します。

`protocol = "usi"` の要素について、動かし方は次のとおりです。

- `command` はそのまま実行されます。サーバーは引数を足さず、環境変数も設定せず、トークンも渡しません。ログインはサーバーの側で行われるので、エンジンがトークンを使うことはありません。サーバーとエンジンのやりとりは標準入出力の USI だけです。エンジンが標準エラーに書いた内容は、サーバーのログと同じ出力先に出ます。
- `lifecycle = "resident"`: サーバーの起動と同時にエンジンを起動し、ログインさせて待機させます。対局が終わると、また待機に戻ります。プロセスが落ちた場合は、間隔を空けながら (1 秒から始めて倍々に、最大 60 秒) 起動し直します。
- `lifecycle = "on-demand"`: ラウンドが必要としたときに起動し、対局が終われば停止します。
- `LOGIN` で名乗る名前は `name`、書かなければエンジン自身の `id name` です。どちらにせよ、その名前が待ち受けの `LOGIN` の規則 (英数字と `_@-.`、1〜1024 文字) を満たさなければ、そのプリセットの起動は失敗し、`name` を書けばよいことをログに出します。
- 対局中、サーバーは対局ごとに `usinewgame` を送り、その対局の `position` 行 (`position startpos moves ...`) と、持ち時間を写した `go` を送ります。`btime` / `wtime` は残り時間、`binc` / `winc` はフィッシャー加算、`byoyomi` は秒読みです。先読み (ponder) はさせません。エンジンが返した指し手は CSA の指し手としてサーバーに送られ、`bestmove resign` は `%TORYO`、`bestmove win` は `%KACHI` になります。対局が終わると `gameover win` / `lose` / `draw` をエンジンに伝えます。時計はサーバーのものがすべてです。

対局中のプリセットは最大 2 つです。数えているのは走っているプロセスの数ではなく、対局に入っているプリセットの数で、次の 2 通りの数え方でちょうど 2 つに収まります。

- `lifecycle = "on-demand"` のプリセット: プロセスを起動した時点から、停止するまで枠を 1 つ使います (これらは対局のためだけに起動され、対局が終われば停止するので、対局の数を数えるのと同じことです)。
- 運用者が動かすプリセットと `lifecycle = "resident"` のプリセット: 対局に組み合わされた時点から、その対局が終わるまで枠を 1 つ使います。待っているだけなら枠は使いません (常駐させること自体がこの `lifecycle` の趣旨なので、待機に枠を課すと対局に入れなくなります)。

組み合わせの側でもこの上限を守ります。枠が足りなくなる組み合わせは作らず、そのプリセットは待ったままになります。プリセット同士の対局は枠を 2 つ、プリセットと外部エンジンの対局は枠を 1 つ使います。

また、同じプリセットが 2 重に起動することはありません。各ラウンドで、待っている外部エンジン (プリセット以外のエンジン) の数を見て次のように動きます。

- 外部エンジンが 0: プリセット同士の対局が走っていなくて、空きが 2 つとプリセットが 2 つあれば、プリセット同士の対局を 1 つ始めます。指定レートの有無は関係ありません。すべてのプリセットに指定レートを与えていても同じように始めます。
- 外部エンジンが 2 以上の偶数: プリセットは起動しません。
- 外部エンジンが奇数: 余る 1 つのために、プリセットを 1 つ用意します。すでに待っているプリセットがあればそれを使います (運用者が動かしているものでも、常駐のものでも同じです)。なければ `lifecycle = "on-demand"` のプリセットを 1 つ起動します。空きがなければプリセット同士の対局を打ち切って空きを作ります。それでも無理なら、そのラウンドは外部エンジンが 1 つ待つことになります。

外部エンジンとの対局が打ち切られることはありません。打ち切られるのはプリセット同士の対局だけで、打ち切られた対局は両者に `#CHUDAN` と `#CENSORED` が送られ、勝敗なし (`none`) の対局として棋譜と行に残ります。打ち切るのは対局に対する操作なので、どちらのプリセットを誰がどう動かしていても同じように働きます。対局が終わったプリセットのうち、`lifecycle = "on-demand"` のものは停止します (待機だけのプロセスを残しません)。運用者が動かしているものと常駐のものは、そのまま待機列に戻ります。

プロセスを起動してから、そのエンジンがログインして待機列に入るまでには時間がかかります。つまりあるラウンドが起動したプリセットを組み合わせるのは、その次以降のラウンドです。運用者が動かすプリセットと常駐のプリセットにはこの待ち時間がありません。すでにログインして待っているので、次のラウンドがそのまま組み合わせます。

レーティングでは、打ち切られた対局は組み合わせによらず対象外です (勝敗がないので)。それ以外は、プリセット同士でも、プリセットと外部エンジンでも、指定レートを持つエンジン同士でも、すべて対象になります。

空の配列 (既定) はプリセットエンジンなしという意味です。`token` はクライアントが実際に提示できるトークンでなければならず (空でない、空白を除く印字可能 ASCII、64 文字以内、`'` を含まない)、重複も許されません。`command` は空文字列の要素を持てません。上の表で「書けない」となっているキーを書いた場合と、`protocol = "usi"` に必要なキーを書かなかった場合も同じです。満たさない要素があると、その要素が何番目かとどのキーの話かを示して起動に失敗します。トークンそのものはログに出ません。

### 局面集

- 設定ファイルとは別のプレーンテキストで、トップレベルの `positions` が指します。1 行 1 エントリ、各行は USI の `position` コマンドです。先頭の `position` キーワードは省略できます。空行は読み飛ばし、CRLF の行末も同じように読みます。
- 局面の起点は `startpos` のみです。
- 起動時に、次の検査を通ります。どれか 1 つでも通らないエントリがあれば、その行番号とともにエラーとして報告し、起動しません。
  - 平手からの合法性。手順を実際に再生し、非合法手があればその行と何手目かを挙げて報告します。
  - 同一局面の 4 回出現。開始局面を 1 回目と数え、手順の途中で 4 回目に達するエントリは、対局開始前に千日手が確定するのでエラーになります。3 回までは指し手で避けられるので通ります。
  - `[limit]` との整合。`max_moves` は開始局面の手順も数えるため、`max_moves` から手順の手数を引いた残りが、実際に指せる手数です。この残りが `min_playable_plies` に満たないエントリはエラーになります。
  - 持ち時間が非対称な場合 (`[time.reduction]` あり) は、さらに 2 つの検査があります。盤面を直接書いたエントリは、減算を載せる手順がないのでエラーになります。手順を書いたエントリは、減らす側の指し手が 1 手も含まれていなければエラーになります。手順が空のエントリは、サーバーが 4 手の玉の往復を補うので通ります。
- 不正な行は最初の 1 行で止めず、すべて行番号付きでまとめて報告します。エントリが 1 つもない局面集を指している場合も起動しません。
